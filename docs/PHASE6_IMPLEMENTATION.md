# Phase 6: tray, independent app status and notification preferences

Branch `codex/phase-6-tray-status` starts at approved Phase 5 integration `378f9fbf245193089ce55271a10e7c0079a5c882`. Scope is Phase 6 only. D22 records the owner's multi-app presentation refinement; the review protocol records authorized Phase 6–9 delivery gates. Historical phase reports remain unchanged.

## Status and lifetime

The serialized Core monitor publishes one copied `StatusSnapshot` collection after authoritative observation commit and exact-instance enforcement. Each enabled app carries its matching quota/downtime facts, decision, observed/grace counters and original committed grace episode. Readers never join separately published state, inspect processes, read SQLite, or evaluate policy. No enforcement algorithm, grace duration/deadline/capture, receipt schema or accounting classification changed.

The tray owns a single WinForms `NotifyIcon`, menu and disposable icon rendered from the existing centralized `ScreenTimeBrandImage` vector. Its appearance stays stable across app states. One-app tooltips show state/remaining allowance; many-app tooltips show monitored/restricted counts without an aggregate allowance. Tooltip updates are bounded to 127 UTF-16 characters and meaningful state/minute changes. Hidden status refresh is every five seconds; a visible panel formats original-deadline countdowns every second. The timer never writes state. Closing the panel returns to the ordinary cadence; shutdown disposes panel, timer, native icon, menu and image.

Left click and Open ScreenTime expose the same password-free singleton collection. Rows sort grace, restriction, running, available, remaining allowance, name and canonical-key ties. Stable row instances preserve expanded Details and scroll position across refresh. Used quota, allowance and remaining appear separately from observed/grace time; running is explicitly last-observed, current downtime and quota reasons coexist, and projections state the no-further-use assumption. Grace denies new sessions and shows the persisted stop time prominently. Current-day full quota remains unavailable during downtime. A bounded list scrolls for many apps; details do not expose mutable controls.

Panel placement uses its opening pointer/monitor anchor, native work-area/window rectangles and WPF DPI bounds, reapplied after content rendering/size changes. An initial Loaded-only implementation grew below the taskbar; screenshot inspection caught this and native full-HWND bounds assertions now cover initial display and detail growth. The accepted automatic notification placement/native-input path was not changed.

## Protected commands

Tray Settings, Exit and the existing settings shortcut route through one `SettingsAccessService`. Every command reads the existing password hash/salt and verifies through the unchanged PBKDF2 helper; no second password store or status-derived authorization exists. Wrong/cancelled authentication executes neither callback. One modal authorization/settings session at a time prevents reentrant stacked settings. Successful Exit uses the existing awaited shutdown; ordinary panel closure does not stop monitoring. Test-only profile events reach these same production command boundaries; the existing fixture stop signal remains limited to test profiles.

Settings compares rule configuration before/after its modal session and reloads the coordinator only if rules changed. Notification-only saves, Cancel and security/display inspection therefore do not reset measured accounting. The existing settings capability remains scoped to that authenticated modal session. Legacy settings/history UI is otherwise retained; no aggregate policy is enabled.

## Presentation preferences and isolation

Standard preserves all six notices, default colors and the full final-minute display. Minimal retains grace start, final countdown and blocked/expired notices. Custom provides independent milestone flags, countdown visibility and 1–60-second duration, optional #RRGGBB informational/warning/critical accents, and reset. Defaults preserve the approved four-state palette (the existing stronger grace-start accent remains unless Warning is customized). Text/body and neutral surface remain unchanged.

The renderer filters requests after receipt/mailbox delivery, so suppressed notices never affect Core decisions. A bounded per-app pending list can wait until the chosen final portion of the original deadline; stale/disabled requests are discarded. No countdown preference writes a deadline, adds a Core wake, changes capture sets, delays enforcement, or performs per-second IO. Best-effort receipts can still record a request that the owner suppresses; they are not proof of display.

`notification-preferences.json` lives in the selected isolated profile. A validated staged file is flushed and atomically replaced. It is independent of both the policy database and receipt writer; save failure cannot take the SQLite policy writer lock. Malformed/unreadable preferences are diagnosed and fall back to Standard without deleting the source or preventing monitoring. Existing UI settings show save failures instead of claiming persistence. No schema migration is needed. Include this file when backing up a profile.

The settings preview constructs only synthetic `Example App` notification facts and the passive renderer. It has no monitor/storage/process/enforcement dependency; it can preview a disabled milestone without changing preferences until Save. Closing/unloading its editor disposes the preview. The separate `--preview-notices` mode remains isolated and database-free.
