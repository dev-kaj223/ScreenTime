# Phase 7 — Reliability and failure handling

Base: `899ed1344137472bed5dcf1e5e871504b2e719b0`, the approved normal Phase 6 merge into `screentime-dev`. This phase implements the owner's approved reliability/fault-testing scope. It adds no watchdog, automatic restart, clock-tamper defense, aggregate policy, import or packaging behavior. Prior phase reports remain unchanged.

## Concrete fixes

- Configuration writes now use one SQLite transaction. Password changes and first-run setup use the same atomic hash/salt operation; authentication reads the pair with one SELECT. Configuration, rule/schedule/downtime, and grace/capture reads use consistent snapshots. PBKDF2-SHA256, salt/hash sizes and iteration count are unchanged. Malformed credentials fail closed without resetting storage.
- A new rule's generated ID is assigned to the caller only after its schedules and blocked periods commit. An INSERT rolled back by a later statement therefore leaves the same object retryable.
- Failed connection initialization disposes its connection. Policy and independent notification-receipt connections use a five-second SQLite busy timeout per operation instead of the default 30 seconds. This bounds busy retries, not arbitrary operating-system IO or total multi-operation shutdown time. Persistent policy-storage failures still fault the supervised monitor/application; they do not authorize uncommitted permission, uncommitted expiry enforcement or a new deadline. There is no automatic database deletion/recreation or availability-policy change.
- Concurrent stop calls share one shutdown task. Late reload, power/time signals and queued test ticks cannot restart work after stopping. The active operation is joined; original worker faults remain observable. The notice outbox completes/drains its mailbox and discards a receipt result that finishes after stop. Process-picker enumeration disposes every `Process` wrapper and tolerates exit/access races.

## Exercised fault and regression coverage

`ReliabilityPersistenceTests` uses actual SQLite transactions, triggers and page-allocation limits: partial credential/config rollback; concurrent consistent reads; rule INSERT rollback and same-object retry; failed connection-initialization cleanup; corrupt/future-schema preservation; `SQLITE_FULL`; and an actual held writer transaction. Expiry failures leave the original episode active and issue no kill; after storage recovery and monitor restart, the original deadline is committed as expired before exact-instance enforcement. `PRAGMA integrity_check` verifies the recovered fixture. The internal connection callback only configures SQLite faults in tests; it has no production caller.

Lifecycle tests overlap 40 stop/reload/power/dispose callers around an active observation, retain the existing supervision/cleanup fault cases, and verify late work cannot reopen sessions. Outbox tests join a blocked receipt writer and verify both ready and in-flight notices are discarded. Concurrent oversized exception logging retains parseable bounded records and one backup. Existing sleep, midnight, grace, same-name ownership, notification-preference isolation and native passive-notice tests remain part of the full suites.

The accelerated observation test performs 1,201 real-persistence ticks, including 1,000 one-second measured intervals and 100 confirmed exits/restarts. It verifies exactly 1,000 observed/quota seconds, zero grace, 101 session rows and zero raw NULL session ends. Its timing samples describe accelerated fake-time/process stress, not real-time game performance.

UI/process integration adds duplicate launch (one surviving original monitor), corrupt-profile startup (nonzero exit and preserved bytes), malformed-credential denial and resource samples of an isolated idle app with one configured absent helper. Only disposable profiles and fixture-owned helpers are used.

## Practical limits

SQLite page exhaustion is a real `SQLITE_FULL` failure on a disposable database; it does not fill the host's disk. Corruption and contention are fixture-local. Resource samples and accelerated stress are finite observations, not multi-day leak/stability guarantees or approved numerical budgets. No hardware suspend/hibernate, real-calendar midnight, game frame-time or new Apex acceptance is claimed. Passive notification rendering, default visuals, focus/input behavior and original deadline algorithms are unchanged; independent review determines whether additional physical acceptance is required.
